02

τ is a geometric series, not a line

Accepting the first token has probability α. Accepting the first two has α². Sum the expected run and you get a closed form that saturates — every extra draft token you add is worth less than the one before it.

τ = (1 − α^(K+1)) / (1 − α),  capped at K+1

03

The free lunch at small batch

Everything is priced in one unit: a single target forward pass over one token position, at the current batch size. That makes vanilla decoding cost exactly 1.0 per token by construction.

At batch 1 the target is bandwidth-bound. Producing one token means streaming all 12B weights out of HBM and doing almost no arithmetic with them. Hand it K+1 positions instead and it streams those same weights once — so verification is very nearly free, and the only real cost is the draft model's own K passes.

04

The collapse at large batch

A GPU kernel takes as long as its slower half. Streaming weights out of HBM and doing arithmetic on them happen concurrently, so the wall-clock is whichever finishes last — that max is the entire roofline, and it is where the formula comes from.

Memory time is fixed. One forward pass reads the model's weights once, no matter how many token positions are in flight. Normalize that to 1 and every other quantity is measured against it.

Compute time scales with the total token positions in the GEMM, which is B·P for batch B and P positions. Define B* as the batch where a single-position pass is exactly balanced — compute time equal to memory time. Then compute time for any pass is B·P / B*, in the same units.

So one pass costs max(1, B·P/B*). We want cost relative to a vanilla token at the same batch, and vanilla is that same expression with P = 1. Divide one by the other:

ratio(P) = max(1, B·P / B*)  /  max(1, B / B*)

Two independent max calls means three regimes, not two. Drag the batch slider and watch which arm of each one wins.

The sting. A single position is still memory-bound, but K+1 positions are not — speculation pushed this batch over the knee by itself. Cost ramps linearly here while vanilla stays flat.

Both arms win. B and B* cancel completely, leaving the position count. Every draft token now costs a full token's worth of FLOPs whether or not it survives verification.

Case B is the one people miss. Plain decoding crosses into compute-bound at B*, but speculation gets there at B*/(K+1) — with K = 4 and B* = 192, that is batch 39 rather than 192. Speculative decoding brings forward the very regime that kills it, and drafting harder brings it forward further.

In the compute-bound regime, K = 4 and α = 0.8 gives τ = 3.36 for 5 verified positions. What went wrong?

05

The adapter tax

Now make the draft repo-specific. One LoRA per repository, all of them resident on one GPU behind one base model, served S-LoRA style: the base weights stay unmerged, and each request's low-rank term is gathered, multiplied, and scattered back — every token, every layer.

Call that overhead A, expressed as a fraction of the compute C it wraps. A/C is not a constant. It drifts upward with batch size, because C per sequence amortizes across the batch while every sequence still drags its own adapter.

06

The gate

Here is the whole project in one inequality. Compare the per-repo draft against a generic draft, not against vanilla. Same K, same c, same verify cost — the only two things that differ are acceptance and the adapter tax. Everything else cancels:

ship ⟺ τ_L / (C + A) > τ_G / C  ⟺  τ_L / τ_G > 1 + A/C

The relative acceptance gain has to clear the relative overhead. That is the entire week-1 decision, and K almost completely drops out of it.

Your call. Week 1 came back. On three repos at K = 4, the generic draft measures α = 0.70. The per-repo adapter measures α = 0.73 — acceptance genuinely improved. The serving harness measures A/C = 8%. Ship it, or kill it?

Debrief

0

Answer the six checkpoints to close out the gate.

What τ is

Expected accepted tokens per step. A geometric series in α that saturates at 1/(1−α), which is why long drafts stop paying. Independent of batch size — what changes is what τ is worth.

Why batch size decides everything

Below B*, verification rides free on a weight stream you were paying for anyway. Above it, every draft position costs real FLOPs and rejected tokens become billed waste.

The tension in one line

Speculative decoding wants small batches. Multi-adapter serving only exists because of large ones. Whether those windows overlap is an empirical question, not a design choice.

The gate itself

τ_L / τ_G > 1 + A/C. Measure both sides on two or three repos before curating a single training example. A 3-point acceptance gain against an 8% tax is a no-go, however good it looks in isolation.

The trap

Reporting speedup against vanilla instead of against a generic draft. Vanilla is the normalizer; the generic draft is the baseline. The headline number is the difference between those two rows.

What this model leaves out

An idealized roofline with no efficiency loss at the knee, and no KV-cache pressure — at high batch and high adapter count, resident adapters shrink the feasible batch. Both make the real picture worse.

A teaching model, not a benchmark. Every constant here is a slider precisely because the honest version of these numbers has to be measured on your own hardware, harness, and repositories.
