1. What this tutorial is & how to use it

Tensara gives you a function signature and a correctness/perf grader, then asks you to write a CUDA C++ kernel. The catalog spans 84 problems across 16 categories — from a one-liner ReLU to MXFP4 GEMM with block-scaled tensor cores to FlashAttention. To solve them all you need a fairly complete CUDA toolkit.

Rather than a problem-by-problem walkthrough, this is organized around the 6 reusable patterns that show up across the catalog (sections 7–11), the specialty topics that don't reduce to those patterns (sections 12–19), and one fully-worked example (section 21, conv-1d). After each pattern section there's a maps to box listing which problems it solves.

First time: read top-to-bottom. Then treat the document as a reference — jump to the pattern section that matches the problem in front of you and the specialty section that matches the data type.

2. The tensara solve() ABI

Every tensara problem expects you to define one function with C linkage: 

extern "C" void solve(/* problem-specific args */);

Universal rules across all 84 problems:

  • All pointer args are device pointers already allocated and populated by the harness. Do not cudaMalloc / cudaMemcpy for them.
  • Parameter order & types are emitted verbatim from each problem's def.py parameters list. Read the signature character by character before you start.
  • Scalar args are passed by value (e.g. const float scaling_factor, int kernel_size).
  • Shape/dim args are sometimes size_t, sometimes int. The variadic-rank problems (softmax, MSE, generic dim reductions) take const size_t* shape, size_t ndim — that shape pointer is a device pointer too. Copy it into shared memory once at kernel entry, don't deref it from every thread.
  • Row-major layout is universal. No NCHW ↔ NHWC ambiguity except for grayscale (which is HWC packed R,G,B,R,G,B,…).
  • Most problems use FP32. The exceptions are the quantization problems (packed FP4/FP8 bytes plus scale bytes) and NVFP4 quantization (FP16 input). Read the signature.
Some tensara web URLs use long slugs (scaled-dot-product-attention) but the API uses short ones (scaled-dot-attention). If you're scripting against the site, hit the /api/trpc/problems.getById?input=… endpoint with the short slug instead of scraping the SSR page.

2.1 Skeleton

#include <cuda_runtime.h>
#include <cstddef>

__global__ void my_kernel(const float* __restrict__ in,
                          float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = in[i];  // your work here
}

extern "C" void solve(const float* in, float* out, size_t n) {
    int block = 256;
    int grid  = ((int)n + block - 1) / block;
    my_kernel<<<grid, block>>>(in, out, (int)n);
}

3. The GPU mental model

3.1 Why GPUs look weird if you come from CPUs

A modern CPU has <10 cores of out-of-order execution, deep pipelines, big private caches, and is optimized to make one stream of instructions as fast as possible. A GPU like an H100 has 132 SMs, each running up to 64 warps (a warp = 32 threads in lockstep). That's potentially ~270 000 threads in flight at once, all sharing a single (huge) memory.

Two consequences shape everything else:

  1. Latency is hidden by parallelism, not avoided. If one warp stalls on a global memory load (~400–600 cycles), the SM scheduler swaps in another warp. As long as you have enough warps, the SM never sits idle.
  2. Throughput per byte from DRAM is precious. H100 HBM3 gives ~3 TB/s of bandwidth across ~67 TFLOPS of FP32 (or ~989 TFLOPS of FP16 tensor cores). The arithmetic intensity (FLOPs per byte) you need to be compute-bound is huge. Almost every "simple" kernel is bandwidth-bound.
CPU = a sushi chef with insanely sharp knives, working alone at one station as fast as possible. GPU = a stadium kitchen with 270 000 line cooks, each slower, but a constantly-moving conveyor belt bringing ingredients. If the conveyor (DRAM) is the bottleneck, no number of fast cooks helps.

3.2 The thread / block / grid hierarchy

When you launch a kernel, you specify two 3D shapes:

  • Block — up to 1024 threads. Threads in the same block can share memory and synchronize.

3.3 How this maps to hardware

Blocks are handed to SMs as resources free up. Once a block lands on an SM, it stays until done. Within the SM, threads are bundled into warps of 32. All threads in a warp execute the same instruction at the same time — SIMT (Single Instruction, Multiple Threads).

Three numbers in your head:
  • 32 — threads per warp. Almost every performance rule is "per warp": coalescing, bank conflicts, shuffles, divergence. Block sizes should be multiples of 32.
  • 1024 — max threads per block.
  • 48–228 KB — shared memory per block, depending on GPU and opt-in.

3.4 Divergence

A warp executes one instruction at a time. If an if goes different ways on different threads in the same warp, the warp executes one branch with the other threads masked off, then the other branch — both paths run sequentially. 

// fine: all 32 threads in the warp take the same branch
if (blockIdx.x == 0) { ... }

// fine: divergence only at one warp at the edge
if (i < N) { do_work(); }

// bad: half the warp does one thing, half does another
if (i % 2 == 0) { even_work(); } else { odd_work(); }

Edge-case divergence (one warp at the boundary) is normal and cheap. Per-thread divergence in the hot loop is what you avoid.

4.1 Vector add — the hello world

__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

// launch
int block = 256;
int grid  = (n + block - 1) / block;     // ceil divide
vec_add<<<grid, block>>>(d_a, d_b, d_c, n);

The <<<grid, block, smem_bytes, stream>>> syntax is the only non-C++ piece of CUDA. The 3rd argument is dynamic shared memory bytes (often 0), the 4th is the stream.

4.2 Picking block size

Must be a multiple of 32. Defaults that work well:

  • 256 for most kernels — safe starting point.
  • 128 for register-heavy kernels (matmul tiles, attention).
  • 512–1024 for memory-bound element-wise kernels where you want fewer blocks total.

Profile, then tune.

4.3 2D launch geometry for images

For 2D / 3D data, a 2D block shape makes neighborhood indexing natural and keeps coalescing tidy: 

dim3 block(16, 16);                                   // 256 threads, 2D
dim3 grid((W + 15) / 16, (H + 15) / 16);
image_kernel<<<grid, block>>>(img, out, H, W);

// inside the kernel:
int col = blockIdx.x * blockDim.x + threadIdx.x;
int row = blockIdx.y * blockDim.y + threadIdx.y;
if (row < H && col < W) {
    int idx = row * W + col;                          // row-major
    ...
}

Notice: threadIdx.x ↔ column. That makes consecutive threads access consecutive memory addresses (row-major), which gives you coalescing for free.

5.1 Registers

Every local variable lives in a register if it can. ~64K 32-bit registers per SM, split across all resident threads. If each thread uses too many, fewer threads fit per SM (lower occupancy). Check "Registers per thread" in nsight compute — under 32 is usually fine.

5.2 Shared memory

Per-block scratchpad. Two declaration styles:

__global__ void k(...) {
    __shared__ float tile[256];      // static, size known at compile time
    // or
    extern __shared__ float dyn[];   // dynamic, size from launch: k<<<g,b,BYTES>>>(...)
}

All threads in the block see the same shared array. It's how threads cooperate: load once from global, reuse many times from shared. The single most important optimization in stencil / convolution / matmul.

For more than 48 KB of shared memory per block you need to opt in: 

cudaFuncSetAttribute(my_kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, 100 * 1024);

5.3 Constant memory

64 KB region of device memory with a special broadcast cache. Optimal when every thread in a warp reads the same address (1 broadcast, free for 32 threads). Degenerates to global when threads read different addresses (serialized). 

__constant__ float c_kernel[256];                     // file scope, fixed size

// host
cudaMemcpyToSymbol(c_kernel, h_kernel, K * sizeof(float));

Great for small conv kernels (K≤13) and the weight matrix of tiny linear layers. Useless for our conv-1d at K=8191 because threads read different B[j] on each iteration.

5.4 Global memory & coalescing

Your cudaMalloc region. The single most important rule: when a warp issues a load, the hardware looks at the 32 addresses and serves them with as few transactions as possible. A transaction is 32 bytes (a sector) or up to 128 bytes (a cache line). If the 32 threads want 32 consecutive 4-byte words, one transaction satisfies the warp. If the 32 threads want scattered addresses, each can need its own transaction — up to 32× slower.

Each colored cell = a 4-byte word a thread reads. White outlines = one 128-byte memory transaction. Coalesced = 1 transaction. Stride 8 = 8 transactions = 8× slower bandwidth.

Design rule: arrange your loads so threadIdx.x maps to the fastest-varying memory index. For row-major A[row][col], that means col = threadIdx.x + ..., not row = threadIdx.x + ....

5.5 Vectorized loads (float2, float4, uint4)

const float4* A4 = reinterpret_cast<const float4*>(A);
float4 v = A4[i];          // loads 16 bytes in one instruction

Fewer instructions, better memory-controller efficiency. Requires 16-byte alignment of the base pointer (tensara's cudaMalloc gives 256-byte alignment, so OK at offset 0; care with sub-arrays). uint4 is the trick for vectorized loads of packed-byte data (e.g. 16 bytes = 32 packed FP4 values).

5.6 Bank conflicts in shared memory

Shared memory is organized as 32 banks of 4 bytes, interleaved. Within a warp, if two threads access different 4-byte addresses that hit the same bank, the accesses serialize. If they hit the same address, the hardware broadcasts — no conflict.

Classic trap: column access of a 32-wide tile sends all 32 threads to bank 0 (32-way conflict, 32× slowdown). Classic fix: declare the tile one column wider (__shared__ float tile[32][33]) so rows are offset by one bank.

5.7 Local memory (the trap)

Despite the name, "local" memory lives in global memory. It's what registers spill into when you use too many, or when you index a private array with a non-constant index: 

float tmp[64];
for (int i = 0; i < 64; ++i) tmp[i] = i * 2.0f;
out[t] = tmp[t & 63];          // dynamic index → spills to local (= global!)

This silently kills perf. nsight compute shows "Local Memory Overhead" — aim for 0.

5.8 Read-only path / __ldg

Modern GPUs have a separate read-only cache. The compiler uses it automatically when you mark the pointer const __restrict__. Equivalent to manual __ldg(&A[i]). Always do this for inputs unless you have a reason not to.

6. Sync, warps, atomics

6.1 __syncthreads()

A barrier across one block. Every thread must reach the same call before any proceed. Use it after loading shared memory and before reading from it. Do not put it inside divergent code paths.

6.2 Warp-level primitives

Threads in the same warp can communicate faster than going through shared memory.

PrimitiveWhat it does
__shfl_sync(mask, val, src)Every thread reads val from lane src. Broadcast.
__shfl_up_sync(mask, val, delta)Each thread reads from lane-delta. For scans.
__shfl_down_sync(mask, val, delta)Each thread reads from lane+delta. For reductions.
__shfl_xor_sync(mask, val, lane_mask)Butterfly exchange — standard warp-reduction pattern.
__ballot_sync(mask, pred)Each thread's bool becomes one bit of a 32-bit result. Stream compaction.

The canonical warp sum (32 floats → total in lane 0, no shared mem):

__device__ inline float warp_reduce_sum(float v) {
    for (int offset = 16; offset > 0; offset /= 2)
        v += __shfl_down_sync(0xffffffff, v, offset);
    return v;
}

6.3 Atomics

atomicAdd(&c[i], v) reads-adds-writes indivisibly. Works on global and shared. Cheap when contention is low, expensive when many threads hit the same address. Float atomics are supported on compute capability 6.0+ (Pascal+) which means all tensara GPUs.

Pattern: avoid global atomics in inner loops. Reduce to a per-block accumulator first, then issue one global atomic per block.

7. Pattern A — Element-wise & fused epilogues

The simplest pattern. Each thread produces one (or several) outputs, no neighbor data needed. Bandwidth-bound by definition: read inputs, do some math, write output.

7.1 The grid-stride loop

When you don't know N at compile time, or you want one kernel to handle any N, use a grid-stride loop: 

__global__ void scale(float* a, int n, float s) {
    int stride = blockDim.x * gridDim.x;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride)
        a[i] *= s;
}

Cap grid size at something like min(grid_compute, 4 * SM_count) — bigger grids don't help once the GPU is full.

7.3 Branchless writes

For pixel thresholding (out = (in > t) ? 255.f : 0.f), the branchless form lets the compiler emit a predicated store with no divergence cost: 

out[i] = (in[i] > t) ? 255.f : 0.f;          // compiler may emit predicate
// or explicit:
out[i] = ((float)(in[i] > t)) * 255.f;

7.4 The fused-epilogue idea

Whenever the problem says "compute X then apply Y", do both in one kernel. Compute X in registers, apply Y in registers, store once. Never materialize the intermediate to global. This is what saves you a full pass over the data — usually a 2× bandwidth win. 

// Bad: two kernels, two passes over conv result
__global__ void conv(...);
__global__ void relu_hardswish(...);

// Good: one kernel, conv accumulator → relu → hardswish → store
__global__ void conv_relu_hardswish(...) {
    float c = compute_conv_output(...);
    float r = fmaxf(0.f, c);                              // ReLU
    float h = r * fminf(6.f, fmaxf(0.f, r + 3.f)) / 6.f;  // HardSwish
    out[i] = h;
}

7.5 Image indexing

HWC packed RGB (the tensara grayscale problem): rgb[(row * W + col) * 3 + c] for c ∈ {0, 1, 2}. The three channels for one pixel are adjacent in memory — one thread can load them as a float3 (12 bytes, padded to 16 for alignment). Grayscale formula: Y = 0.299 R + 0.587 G + 0.114 B.

Maps to: ReLU, Leaky-ReLU, GELU, Sigmoid, Tanh, ELU, SELU, Softplus, Swish, Hard-Sigmoid · Vector Addition · Matrix Scalar Multiplication · Huber Loss, Hinge Loss (per-element) · Image Thresholding, Grayscale Conversion · ECC Point Negation · Vector Multiplication over Finite Field · MXFP4 / MXFP8 / NVFP4 Dequantization · the epilogues of every fused-GEMM problem (GEMM+bias+ReLU, matmul-swish, matmul-swish-scaling, gemm-multiply-leakyrelu, conv2d-relu-hardswish).

8. Pattern B — Stencils with halos

A stencil kernel computes each output as a function of a window of inputs around the same position — convolution, pooling, edge detection, blur. The pattern: each block claims a contiguous tile of output, cooperatively loads the input window (data + halo) into shared memory once, syncs, then every thread reads only from shared. Bandwidth pressure drops by a factor of (reuse count).

8.1 Halos / ghost cells

A block computing outputs [i, i+BLOCK) needs inputs [i-r, i+BLOCK+r) for radius r = (K-1)/2. The r overhang on each side is the halo.

Green = output tile this block computes. Orange = halo cells in shared memory but not "owned." Tile size = BLOCK + 2r = 144 floats. Halo overhead shrinks as block size grows, but too big and you exhaust shared memory.

8.2 1D stencil kernel sketch

template<int BLOCK>
__global__ void stencil_1d(const float* __restrict__ A, float* __restrict__ C,
                           int N, int r) {
    __shared__ float tile[BLOCK + 2 * MAX_R];
    int tile_start = blockIdx.x * BLOCK;

    // 1. cooperative load (BLOCK threads cover BLOCK + 2r elements)
    for (int t = threadIdx.x; t < BLOCK + 2*r; t += BLOCK) {
        int g = tile_start - r + t;
        tile[t] = (g >= 0 && g < N) ? A[g] : 0.0f;        // zero-pad
    }
    __syncthreads();

    // 2. compute one output per thread, reading only shared memory
    int i = tile_start + threadIdx.x;
    if (i < N) {
        float acc = 0.0f;
        #pragma unroll
        for (int j = 0; j < K; ++j)
            acc += tile[threadIdx.x + j] * kernel_j;   // kernel_j from constant or shared
        C[i] = acc;
    }
}

8.3 2D and 3D extensions

In 2D you load a (BLOCK_Y + 2r) × (BLOCK_X + 2r) shared tile. Watch shared-memory budget: a 16×16 block with r=2 needs 20×20 = 1.6 KB — trivial. A 32×32 block with r=8 needs 48×48 = 9 KB. In 3D it explodes: an 8×8×8 block with r=5 needs 18³ = ~23 KB. Move to 2.5D tiling: tile (x,y) in shared memory, walk z with a register-window of K planes.

Branch at the load, not in the hot inner loop — that's what the (g >= 0 && g < N) ? A[g] : 0.0f trick gives you. Even better for the "interior vs edge" split: launch one kernel for interior blocks (no boundary checks needed) and another for the few edge blocks.

8.5 Stride and dilation (pooling)

Pooling adds two parameters: stride S (how far the window jumps per output) and dilation D (spacing between taps inside the window). Output length: 

H_out = floor((H + 2*P - D*(K-1) - 1) / S) + 1

Effective radius for shared-mem tiling: r = D * (K-1) / 2. Input index for output o, tap m: S*o + D*m - P.

8.6 Constant memory for small conv kernels

If K × K ≤ 16384 floats (= 64 KB), put the conv weights in __constant__ memory. Every thread in a warp reads the same B[j] on iteration j → broadcast cache → free. Falls apart for the big kernels (conv-1d K=8191, conv-2d K=127) where you should use shared instead.

8.7 Separable convolution

A 2D convolution is separable if its 2D kernel is a rank-1 outer product of two 1D kernels. Cost drops from O(K²) to O(2K) per output. Box blur (all-ones kernel) is separable: do two passes of width-K averaging, one horizontal then one vertical.

8.8 Large-kernel strategies

At K=127 (conv-2d) or K=8191 (conv-1d, 1d-running-sum), direct stencil isn't competitive:

  • im2col + GEMM: unroll the input window into a (H*W) × (K*K) matrix, multiply against the kernel as a (K*K) × 1 matrix using a cuBLAS GEMM.
  • FFT convolution: O(N log N) via cuFFT — asymptotically optimal for very large K.
  • Prefix-sum reformulation: for uniform kernels (all ones), use an integral image. 1D-running-sum reduces to a prefix scan + one subtraction per output — O(N) not O(N·K).
Maps to: 1D Convolution, 2D Convolution, 3D Square Convolution, 2D Conv + ReLU + HardSwish (with fused epilogue), Box Blur (separable), Edge Detection (3-tap stencil) · 1D / 2D / 3D Average Pooling, 1D / 2D / 3D Max Pooling · 1D Running Sum (via prefix scan, see section 10).

9. Pattern C — Reductions

Sum, max, argmax, product, dot, norm — all are reductions: combine N values via an associative op into 1 value. Three regimes by output shape:

  1. Scalar output (MSE, triplet loss, MST argmin) — one number from the whole tensor.
  2. Per-row output (RMSNorm, L1/L2, log-softmax, cosine-similarity) — one number per row of a 2D matrix.
  3. Reduction-over-arbitrary-dim (sum/max/mean/product/argmax over a chosen dim of an arbitrary-rank tensor) — one number per "outer × inner" coordinate.

9.1 Warp reduction with shuffles

__device__ inline float warp_sum(float v) {
    for (int o = 16; o > 0; o /= 2)
        v += __shfl_down_sync(0xffffffff, v, o);
    return v;        // lane 0 holds the result
}

Replace += with fmaxf for max, etc. Cost: 5 shuffles. No shared memory needed.

9.2 Block reduction (warp → shared → warp)

__device__ float block_sum(float v) {
    __shared__ float warp_partial[32];                    // up to 32 warps per block
    int lane = threadIdx.x & 31;
    int wid  = threadIdx.x >> 5;

    v = warp_sum(v);                                      // one number per warp
    if (lane == 0) warp_partial[wid] = v;
    __syncthreads();

    // first warp reduces the partials
    v = (threadIdx.x < (blockDim.x + 31) / 32) ? warp_partial[lane] : 0.0f;
    if (wid == 0) v = warp_sum(v);
    return v;                                             // valid in thread 0
}

9.3 Whole-tensor reduction (scalar output)

Two clean approaches:

  • One kernel, atomicAdd: each block produces a partial via block_sum, then thread 0 issues one atomicAdd into the output scalar. Non-deterministic ordering, but fine for FP32 sums that pass tolerance.
  • Two kernels: first writes one float per block to a workspace; second reduces the workspace. Deterministic. Marginal extra cost.

Initialize the output scalar to 0 via cudaMemsetAsync before launching.

9.4 Key-value reduction (argmax)

Shuffle both value and index, take the better pair. Strict > gives "first occurrence" tie-break: 

__device__ void warp_argmax(float &v, int &idx) {
    for (int o = 16; o > 0; o /= 2) {
        float ov = __shfl_down_sync(0xffffffff, v, o);
        int   oi = __shfl_down_sync(0xffffffff, idx, o);
        if (ov > v) { v = ov; idx = oi; }                  // strict > = first index wins
    }
}

9.5 Generic n-D dim reduction

Given shape[] and dim, decompose the tensor as (outer, axis, inner) where 

outer       = product of shape[0..dim-1]
axis        = shape[dim]
inner       = product of shape[dim+1..ndim-1]
input[o, a, k]   = input_flat[o * (axis*inner) + a * inner + k]
output[o, k]     = reduce over a of input[o, a, k]

Two regimes with very different kernels:

  • dim is innermost (inner = 1) — the reduction axis is contiguous. One block per output row, threads cooperate along the axis, coalesced loads. Use the block-reduction pattern from 9.2.
  • dim is outer / middle — reduction is strided. Map one output to one thread (or a small group). Each thread strides through axis values inner apart. Loads are coalesced across threads (different k) but not within a thread.

9.6 Multi-reduction fusion

Cosine similarity needs three sums per row: ∑xy, ∑xx, ∑yy. Run all three in the same loop in registers, then reduce a struct via shuffles: 

float sxy = 0, sxx = 0, syy = 0;
for (int k = threadIdx.x; k < D; k += blockDim.x) {
    float x = X[r*D + k], y = Y[r*D + k];
    sxy += x*y; sxx += x*x; syy += y*y;
}
sxy = warp_sum(sxy);
sxx = warp_sum(sxx);
syy = warp_sum(syy);

9.7 Welford's online variance (BatchNorm, LayerNorm)

Naive mean+variance via "sum and sum-of-squares" can lose precision when values are large. Welford's algorithm tracks (count, mean, M2) incrementally; the parallel combine rule is: 

// merge B into A
n  = nA + nB
d  = meanB - meanA
mean = meanA + d * (float)nB / (float)n
M2   = M2A + M2B + d*d * (float)(nA * nB) / (float)n
// variance = M2 / n   (or M2 / (n-1) for sample variance)

Implement this as a warp-shuffle reduction over (n, mean, M2) triples. Required for LayerNorm and BatchNorm under tight tolerances and large per-row reductions (up to 4M elements per row for LayerNorm).

10. Pattern D — Parallel scans

A scan turns [a, b, c, d] into [a, a+b, a+b+c, a+b+c+d] (inclusive) or [0, a, a+b, a+b+c] (exclusive). Sequential algorithm is O(N) work, but the dependency chain looks fatal for parallelism. There are clever ways to do it in O(N) work and O(log N) depth.

10.1 Hillis–Steele (work-inefficient, conceptually easy)

Each step doubles the offset. For N elements: log N steps, N log N work. Implementable in one warp with __shfl_up_sync: 

__device__ float warp_inclusive_scan(float v) {
    for (int o = 1; o < 32; o *= 2) {
        float n = __shfl_up_sync(0xffffffff, v, o);
        if ((threadIdx.x & 31) >= o) v += n;
    }
    return v;
}

10.2 Blelloch (work-efficient)

Two phases on a balanced binary tree: up-sweep (compute partial sums going up) and down-sweep (push prefixes back down). Total work O(N), depth O(log N). The production pattern inside a block.

10.3 Multi-block scan: scan-then-fan

For N too large to fit in one block (cumsum at N=1M):

  1. Scan each block locally with Blelloch; write per-block totals to a length-numBlocks array.
  2. Scan the per-block totals (small, fits in one block).
  3. Fan back: add the scanned block-total to every element of the corresponding block.

10.4 Decoupled lookback (CUB)

Single-pass GPU scan due to Merrill & Garland: each block computes its local scan and aggregate, then uses atomic flags to fetch and combine predecessor aggregates without two full kernel passes. This is what cub::DeviceScan::InclusiveSum uses under the hood — if you don't need to learn it from scratch, just call CUB.

10.5 Library escape hatch

#include <cub/cub.cuh>
size_t temp_bytes = 0;
cub::DeviceScan::InclusiveSum(nullptr, temp_bytes, in, out, N);
void* temp;

10.6 Sliding-window reformulation via prefix sum

1D-running-sum (K=8191) is the canonical example: instead of a stencil, do an inclusive scan once, then output[i] = prefix[i + r] - prefix[i - r - 1] (with boundary fixup). O(N) instead of O(N·K). Generalizes to 2D as the summed-area table / integral image trick used in box-blur.

Maps to: Cumulative Sum, Cumulative Product · 1D Running Sum (via prefix difference) · Box Blur (via integral image) · Radix-sort histogram offsets (see section 11).

11. Pattern E — Numerically stable & online softmax

Naive softmax(x_i) = exp(x_i) / sum_j exp(x_j) overflows when any x_i is large. The fix is to subtract the max first — mathematically identical, numerically safe.

11.1 Standard two-pass softmax

// Per row:
// Pass 1: m = max_j x[j]
// Pass 2: s = sum_j exp(x[j] - m)
// Write:  out[i] = exp(x[i] - m) / s
__global__ void softmax_2pass(const float* X, float* Y, int M, int N) {
    int row = blockIdx.x;
    // -- pass 1: reduce max --
    float m = -INFINITY;
    for (int k = threadIdx.x; k < N; k += blockDim.x) m = fmaxf(m, X[row*N + k]);
    m = block_max(m);    // broadcast lane-0 max into shared, then to all threads
    __shared__ float row_max; if (threadIdx.x == 0) row_max = m; __syncthreads();
    m = row_max;

    // -- pass 2: reduce sum-of-exps --
    float s = 0;
    for (int k = threadIdx.x; k < N; k += blockDim.x) s += __expf(X[row*N + k] - m);
    s = block_sum(s);
    __shared__ float row_sum; if (threadIdx.x == 0) row_sum = s; __syncthreads();
    s = row_sum;

    // -- write --
    for (int k = threadIdx.x; k < N; k += blockDim.x)
        Y[row*N + k] = __expf(X[row*N + k] - m) / s;
}

11.2 Log-softmax

log_softmax(x_i) = x_i - m - log(sum_j exp(x_j - m)). Same two passes, last line writes x[k] - m - logf(s). The tensara log-softmax problem spec explicitly mandates this form.

11.3 Online (streaming) softmax

The two-pass softmax reads X three times. The online softmax trick (Milakov & Gimelshein 2018) does it in one pass by carrying a running (max, normalizer) pair and rescaling when the max changes. It's the foundation of FlashAttention. 

// One pass: combine (m_old, s_old) with each new chunk of x's:
//   m_new = max(m_old, m_chunk)
//   s_new = s_old * exp(m_old - m_new) + s_chunk * exp(m_chunk - m_new)
//
// Initialize: m = -inf, s = 0.

float m = -INFINITY, s = 0.0f;
for (int k = threadIdx.x; k < N; k += blockDim.x) {
    float x   = X[row*N + k];
    float m_n = fmaxf(m, x);
    s = s * __expf(m - m_n) + __expf(x - m_n);
    m = m_n;
}
// reduce (m, s) across threads with the same combine rule, then write outputs

The parallel combine for (m, s) across two halves A and B: 

m_AB = max(m_A, m_B)
s_AB = s_A * exp(m_A - m_AB) + s_B * exp(m_B - m_AB)
Maps to: Softmax, Log Softmax · Scaled Dot-Product Attention (see section 19) · the safe-exp normalization inside KL divergence and any cross-entropy-flavored loss you might write later.

12. GPU sorting

Three algorithms worth knowing, in order of practical importance on tensara's array-sort:

12.1 Radix sort (the practical one)

For fixed-width integer keys (32-bit ints in array-sort), radix is the workhorse: O(N·keysize) passes of (histogram → scan → scatter). The internal scan step is exactly what section 10 taught. Use CUB:

12.2 Bitonic sort

A sorting network with O(log² N) depth. Maps cleanly to GPU because the comparisons at each step are independent. Single-block bitonic sorts up to ~2048 elements in shared memory; for larger arrays you tile and merge.

12.3 Merge sort

Comparison-based, stable. Less common on GPU than radix but useful when keys aren't fixed-width or you need stability. thrust::sort uses a hybrid radix/merge.

13. Tiled matrix multiplication

GEMM is the most important GPU kernel because every neural network is mostly matmul, and because it's the textbook example of how to be compute-bound rather than bandwidth-bound. Tensara has 14 matmul variants — learn the canonical tiled GEMM once and the variants follow.

13.1 The output-stationary tile

Compute C = A @ B with A: M×K, B: K×N, C: M×N. Each block computes a BM × BN tile of C. To compute that tile we need a BM × K slice of A and a K × BN slice of B. We don't load them all at once; we walk the K dimension in chunks of size BK: 

for (int k0 = 0; k0 < K; k0 += BK) {
    load A[BM, BK] into shared    // cooperative, coalesced
    load B[BK, BN] into shared
    __syncthreads();
    for (int k = 0; k < BK; ++k)
        accumulate outer product As[:, k] x Bs[k, :] into register tile
    __syncthreads();
}
write register tile to C[BM, BN]

13.2 Register tiling

Each thread doesn't compute one output of C — it computes a TM × TN sub-tile in registers. Typical: BM=BN=128, BK=8, threads per block = (BM/TM) * (BN/TN), TM=TN=8. That gives 16×16 = 256 threads per block, each accumulating an 8×8 register tile = 64 FMAs per K step.

13.3 Vectorized loads & bank-conflict avoidance

Load A and B as float4 when possible. Pad the shared tile's leading dimension by 1 (__shared__ float As[BK][BM + 1]) to dodge 32-way bank conflicts during column reads.

13.4 Tile-quantization (non-multiple-of-tile)

Tensara's square-matmul tests N = 6144, 7168, 9216 — not multiples of 128. Two options: (a) pad with zeros in the loads and mask the store, or (b) write a separate "edge" kernel for the last partial tile.

13.5 Skeleton (FP32, no tensor cores)

template<int BM, int BN, int BK, int TM, int TN>
__global__ void gemm_sm(const float* A, const float* B, float* C,
                        int M, int N, int K) {
    __shared__ float As[BK][BM + 1];
    __shared__ float Bs[BK][BN + 1];
    int block_row = blockIdx.y * BM;
    int block_col = blockIdx.x * BN;
    int thread_row = (threadIdx.x / (BN / TN)) * TM;
    int thread_col = (threadIdx.x % (BN / TN)) * TN;
    float acc[TM][TN] = {{0}};

    for (int k0 = 0; k0 < K; k0 += BK) {
        // cooperative loads (omitted for brevity — vectorize)
        load_tile_A(As, A, block_row, k0, M, K);
        load_tile_B(Bs, B, k0, block_col, K, N);
        __syncthreads();

        #pragma unroll
        for (int k = 0; k < BK; ++k) {
            float a_frag[TM], b_frag[TN];
            #pragma unroll
            for (int i = 0; i < TM; ++i) a_frag[i] = As[k][thread_row + i];
            #pragma unroll
            for (int j = 0; j < TN; ++j) b_frag[j] = Bs[k][thread_col + j];
            #pragma unroll
            for (int i = 0; i < TM; ++i)
                #pragma unroll
                for (int j = 0; j < TN; ++j)
                    acc[i][j] = fmaf(a_frag[i], b_frag[j], acc[i][j]);
        }
        __syncthreads();
    }
    // write acc to C with optional fused epilogue
    write_tile(C, acc, block_row + thread_row, block_col + thread_col, M, N);
}

After the K-loop, before the store: apply bias broadcast, activation (ReLU / LeakyReLU / Swish / HardSwish), scaling. Multiple tensara problems are "GEMM + something" — never write an intermediate M×N tensor; do it in registers.

Maps to: Matrix Multiplication, Square Matrix Multiplication · GEMM with Bias and ReLU, Matrix Multiplication with Swish Activation, Matrix Multiplication with Swish and Scaling, GEMM with Element-wise Multiply and LeakyReLU, Matrix Multiplication with Sigmoid and Sum (with reduction epilogue from section 9).

                          int M, int N, int K) {

    fragment<matrix_b, 16, 16, 16, half, col_major> bFrag;

14.3 TF32 mode for FP32 inputs

Most tensara matmul problems are FP32 but with rtol ~ 1e-3. TF32 (8-bit exponent like FP32, 10-bit mantissa like FP16) rounds the inputs slightly but keeps the dynamic range — usually within tolerance. To enable for cuBLAS: cublasSetMathMode(handle, CUBLAS_TF32_TENSOR_OP_MATH). For raw mma.sync: use the tf32 operand type.

cuda::memcpy_async + the pipeline API (cuda/pipeline) lets you issue a load for the next K tile while the current K tile's mma is still in flight. This hides shared-memory load latency completely. Hopper adds TMA (Tensor Memory Accelerator) for whole-tile async copies.

15. Special-structure matmul

15.1 Triangular GEMM (upper / lower)

Both inputs are triangular and so is the output. Skip tiles entirely below the diagonal (return early if block_row > block_col), and tighten the K-range per tile to [block_row*BM, (block_col+1)*BN]. Total work drops to ~1/6 of dense. Diagonal-major tile ordering load-balances better.

15.2 Symmetric GEMM

If A is symmetric, you can read only the upper triangle and broadcast (halves DRAM traffic from A). In practice on H100 the difference is small — a well-tuned dense GEMM often wins.

15.3 Diagonal GEMM

diag(a) @ B is a row-wise scale, not a matmul. O(N·M) not O(N²·M). One thread block per row: load a = diag[row] into a register, multiply that row of B element-wise. float4 loads on B, no shared memory needed.

15.4 GEMV

Matrix-vector is memory-bound, not compute-bound. Assign one warp (or one block of warps) per output row; warp-reduction of partial dot products via __shfl_down_sync. Cache the vector in shared memory once. For very tall A, splitK with atomicAdd into c[i].

15.5 Batched matmul via grid-z (3D / 4D tensor-matrix)

(N, M, K) @ (K, L) → (N, M, L) is literally one big GEMM with row count N·M. Reshape conceptually, run the dense GEMM. For 4D (B,I,J,L) @ (L,K), collapse (B,I,J) to one dimension. Watch for int32 overflow on N·M — use size_t indexing throughout.

15.6 Matrix N-th power

Chain GEMMs with one scratch buffer. Exponentiation by squaring: 2 mults for n=2 (just A@A), 2 for n=4 (A² then A²@A²), 3 for n=8. Allocate one workspace via cudaMalloc inside solve(), ping-pong with the output.

15.7 SplitK with atomics

For tall-skinny GEMM (large K, small M) the K-direction parallelism dominates compute. Split K across multiple blocks that each compute a partial output, then atomically accumulate. Loses some determinism; watch tolerances.

Maps to: Symmetric / Upper-Triangular / Lower-Triangular / Diagonal Matrix Multiplication · Matrix-Vector Multiplication · 3D / 4D Tensor-Matrix Multiplication · Matrix N-th Power.

16. Quantized GEMM: MXFP4, MXFP8, NVFP4

These are the modern low-precision formats for training and inference at scale. They share three ingredients: (1) a packed low-bit numeric, (2) a per-block scale, and sometimes (3) a per-tensor global scale. To solve the dequantize / quantize / GEMM problems you need to unpack, apply scales correctly, and ideally feed the tensor cores.

16.1 The bit layouts

16.2 Packed access

FP4 packs two values per byte: lo = b & 0xF, hi = b >> 4. Vectorize: load 16 bytes as a uint4 = 32 packed FP4 values in one transaction. 

__device__ inline float decode_e2m1(uint8_t nibble) {
    int sign = (nibble >> 3) & 1;
    int exp  = (nibble >> 1) & 0x3;
    int mant = nibble & 0x1;
    float v;
    if (exp == 0) v = 0.5f * (float)mant;                    // subnormal: 0 or 0.5
    else          v = ldexpf(1.0f + 0.5f * (float)mant, exp - 1);
    return sign ? -v : v;
}

16.3 Block scaling in the GEMM inner loop

MX formats: per-32-element block scale, one E8M0 byte per block. NV formats: per-16-element block scale, one E4M3 byte per block plus a global FP32 scale. Per-block scale lives outside the inner accumulator: load it once per K-block, multiply the K-block's partial sum by it before adding to the running total. 

// MXFP4 GEMM K-loop sketch (one warp computing one output)
float acc = 0;
for (int k0 = 0; k0 < K; k0 += 32) {
    float scaleA = exp2f((float)scaleA_byte[k0/32] - 127.f);
    float scaleB = exp2f((float)scaleB_byte[k0/32] - 127.f);
    float partial = 0;
    for (int k = 0; k < 32; ++k)
        partial += decode_e2m1(A[...]) * decode_e2m1(B[...]);
    acc += scaleA * scaleB * partial;
}

16.4 Swizzled scale layouts (SWIZZLE_32_4_4)

MXFP8 and NVFP4 GEMM lay out the scale array not as [m, k/block] linear but in a 32×4×4 tile that matches the tensor-core fragment layout. Kernels must understand the swizzle to fetch the correct scale byte for a given (m, k) coordinate. Reference implementations live in CUTLASS and flashinfer.

16.5 Tensor-core MMA with FP4 / FP8

On Hopper, FP8 GEMM uses wgmma.mma_async with E4M3 / E5M2 operands and FP32 accumulator. On Blackwell (sm_100), the new mma.kind::mxf4 and mma.kind::nvf4 instructions take packed FP4 operands and a per-block scale fragment in one PTX op — the hardware applies the scale natively.

16.6 Quantization (the forward direction)

For each block (32 for MX, 16 for NV):

  1. Find amax over the block.
  2. Compute the block scale: for MX, scale_exp = ceil(log2(amax / FP4_max)), clipped into E8M0 range. For NV, the per-block scale is an FP8 E4M3 derived as quantize_e4m3(amax / FP4_max), with an outer per-tensor FP32 scale to fit the FP8 range.
  3. Divide block values by the scale.
  4. Round-to-nearest into the target bit format (E2M1 or E4M3).
  5. Pack the bits (two FP4 per byte for E2M1; one byte per E4M3).

17. Graph algorithms on the GPU

All three tensara graph problems use dense N×N adjacency matrices, which makes them naturally GPU-friendly — you operate on a matrix, not a worklist.

17.1 Blocked Floyd-Warshall (All-Pairs Shortest Path)

The k-loop in classical Floyd-Warshall has a serial dependency, but for any fixed k the (i, j) updates are independent. Blocked FW processes B×B sub-blocks of D in three phases per k-block:

  1. Pivot: update the diagonal block D[k:k+B, k:k+B] internally (it depends on itself).
  2. Cross: update the pivot row and column of blocks (D[k:k+B, :] and D[:, k:k+B]) using the pivot block.
  3. Independent: update every other block using the just-updated row and column.

Each block fits in shared memory. This is the canonical FW GPU pattern.

17.2 Parallel Bellman-Ford for Single-Source Shortest Path

N-1 rounds, each round runs a parallel relaxation: dist[v] = min(dist[v], dist[u] + w[u, v]) for all (u, v). Implemented as a min-plus matrix-vector product: each thread owns an output v, loops over u, takes the min. An early-exit check (any relaxation actually changed something?) lets you stop in O(diameter) rounds instead of O(N).

17.3 Parallel Prim for Minimum Spanning Tree

Maintain in_mst[N] (bool) and key[N] (distance from MST). Each round:

  1. Argmin over key where !in_mst → pick the next vertex u to add. Use a device-wide argmin (one CUB call per round, or a custom warp/block argmin).
  2. Add key[u] to the running total.
  3. Mark in_mst[u] = true.
  4. Relax: for every v, key[v] = min(key[v], A[u][v]).

O(N) rounds × O(N) work each = O(N²) total — fine at the problem sizes. The output is the scalar sum, one float.

Maps to: All-Pairs Shortest Path, Single Source Shortest Path, Minimum Spanning Tree.

18. Modular arithmetic over finite fields

Three tensara problems live in F_p (finite field of prime modulus): ECC point negation, polynomial multiplication, and vector multiplication. All use Mersenne primes (2^31 - 1 or 2^61 - 1) so the modular reduction has a fast bit-trick form.

18.1 Mersenne reduction

For p = 2^n - 1: 

// x mod (2^n - 1):
y = (x & p) + (x >> n);           // first fold
if (y >= p) y -= p;               // at most one extra subtract

For p = 2^31 - 1 with operands < p, the product a*b ≤ (p-1)² < 2^62 — promote to uint64_t before multiplying, then fold.

18.2 64×64→128 primitives (when you outgrow Mersenne tricks)

For general primes (e.g. secp256k1's p), you need 256-bit modular arithmetic. The building blocks on the GPU:

__umulhi(a, b)high 32 bits of 32×32 product
__umul64hi(a, b)high 64 bits of 64×64 product
__byte_perm, __funnelshift_lbitfield manipulation

Reduce with Barrett (precompute mu = floor(2^k / p)) or Montgomery (operate in the ×R domain).

18.3 Polynomial multiply over F_p

Naive: c[i+j] = (c[i+j] + a[i] * b[j]) mod p. O(N²). At tensara's test sizes (N ≤ 1024) one thread per output index works fine: each thread computes c[i+j] by summing over the diagonal of the outer product, taking mod once at the end.

Asymptotically optimal: NTT (Number-Theoretic Transform). Same structure as FFT but over F_p, using a primitive root of unity instead of e^{2πi/N}. Cooley-Tukey applies. Mersenne primes have nice roots of unity, so this is a good showcase — but for N=1024 the naive O(N²) beats NTT overhead on practical GPUs.

18.4 ECC point negation

Trivial in affine coordinates: (x, y) → (x, -y mod p). With Mersenne reduction, just p - y (always positive since 0 ≤ y < p).

Maps to: ECC Point Negation (Batched), Polynomial Multiplication over Finite Field, Vector Multiplication over Finite Field.

19. Attention (FlashAttention)

Scaled dot-product attention is O = softmax(Q K¹ / sqrt(d)) V per (batch, head). The naive 3-step kernel:

  1. Compute S = Q K¹ — an S × S matrix, materialized in DRAM.
  2. Softmax over each row of S.
  3. Compute O = P V.

The S matrix is the killer: for sequence length 2048, S has 2048² = 4M floats per head per batch — and you read/write it 3 times. FlashAttention fuses all three steps into one kernel using the online-softmax trick from section 11, never materializing S.

19.1 The algorithm

// For each query row block Q_i (of Br rows):
//   load Q_i once into shared memory
//   initialize: O_i = 0, m_i = -inf, l_i = 0
//   for each key/value block (K_j, V_j) (of Bc rows):
//       compute S_ij = Q_i @ K_j^T / sqrt(d)        [Br x Bc]
//       m_new = max(m_i, rowmax(S_ij))              [Br]
//       P_ij  = exp(S_ij - m_new)                   [Br x Bc]
//       l_new = exp(m_i - m_new) * l_i + rowsum(P_ij)
//       O_i   = exp(m_i - m_new) * O_i + P_ij @ V_j  [Br x d]
//       m_i, l_i = m_new, l_new
//   O_i = O_i / l_i
//   write O_i

19.2 Launch geometry & tile sizes

Grid (B * H, ceil(S / Br)): one block per (batch, head, query-block). Pick Br, Bc, d so (Br + Bc) * d floats fit in shared memory along with the running stats. Typical: Br = 64, Bc = 64, d = 64 → ~64 KB shared (opt-in needed).

19.3 Mixed precision

Inputs FP16/BF16 for tensor-core throughput, accumulate in FP32 (the running m, l, O are all FP32), cast back to the output dtype at the end. Tensara's attention problem uses FP32 throughout, so this shortcut isn't available there.

19.4 Causal masking (not on the tensara problem, but worth knowing)

Skip key blocks entirely to the right of the query block; mask within the diagonal block.

Maps to: Scaled Dot-Product Attention. The same machinery extends to causal attention, cross-attention, GQA / MQA, and the long-context variants you'd implement in your VSA work.

20. Histograms & atomics

Image histogram is the one place atomics dominate the design. Three flavors, increasing speed:

20.1 Naive global atomics

__global__ void hist_naive(const float* in, int* hist, int N, int bins) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) atomicAdd(&hist[(int)in[i]], 1);
}

Slow: every thread contends on the few "hot" bins.

20.2 Per-block shared-memory privatization

__global__ void hist_shared(const float* in, int* hist, int N, int bins) {
    extern __shared__ int s_hist[];                       // size = bins
    for (int b = threadIdx.x; b < bins; b += blockDim.x) s_hist[b] = 0;
    __syncthreads();

    for (int i = blockIdx.x*blockDim.x + threadIdx.x; i < N; i += gridDim.x*blockDim.x)
        atomicAdd(&s_hist[(int)in[i]], 1);                // atomic on shared = fast
    __syncthreads();

    for (int b = threadIdx.x; b < bins; b += blockDim.x)
        atomicAdd(&hist[b], s_hist[b]);                   // one atomic per bin per block
}

Contention drops from "many threads, few bins, global memory" to "many threads, few bins, shared memory" + "one update per bin per block to global." Typical 10–100× speedup.

20.3 Float histogram (tensara's case)

Tensara wants float* output but exact equality. atomicAdd(float*, float) exists on Pascal+. Either: accumulate as unsigned int in shared, then write floats; or use atomicAdd(float*, 1.0f) directly.

Maps to: Image Histogram. The privatization pattern also generalizes to reductions with hot keys (e.g. computing per-class statistics for batched losses).

21. Worked example: conv-1d end-to-end

Time to put it all together. Tensara's 1D Convolution: signal A of length N, kernel B of length K (odd, < N), output C of length N with zero-padded centered cross-correlation. Test sizes: N ∈ {32K, 65K, 131K, 524K}, all with K = 8191.

K = 8191 is huge. Most textbook conv tutorials assume K = 3 or 5. With K = 8191 our shared-memory halo is 8190 elements and our kernel B alone is 32 KB. Standard tricks need adjustment.

21.1 The naive kernel (works, slow)

__global__ void conv1d_naive(const float* __restrict__ A,
                             const float* __restrict__ B,
                             float* __restrict__ C,
                             int N, int K, int r) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= N) return;
    float acc = 0.0f;
    for (int j = 0; j < K; ++j) {
        int idx = i + j - r;
        if (idx >= 0 && idx < N) acc += A[idx] * B[j];
    }
    C[i] = acc;
}

Correct, ~15 lines, passes the easy correctness test. But does N*K ≈ 4.3 G global loads from A for the smallest test case. Bandwidth-bound, way below peak.

21.2 Tiled + halo kernel (the standard win)

Each block computes BLOCK outputs. Load BLOCK + 2r A-values plus all K B-values into shared. Each A is read from global once, reused by up to K threads from shared. 

template<int BLOCK>
__global__ void conv1d_tiled(const float* __restrict__ A,
                             const float* __restrict__ B,
                             float* __restrict__ C,
                             int N, int K, int r) {
    extern __shared__ float smem[];
    float* tileA = smem;                                  // size BLOCK + 2r
    float* tileB = smem + BLOCK + 2 * r;                  // size K

    int tile_start = blockIdx.x * BLOCK;

    for (int t = threadIdx.x; t < BLOCK + 2*r; t += BLOCK) {
        int g = tile_start - r + t;
        tileA[t] = (g >= 0 && g < N) ? A[g] : 0.0f;
    }
    for (int t = threadIdx.x; t < K; t += BLOCK)
        tileB[t] = B[t];

    __syncthreads();

    int i = tile_start + threadIdx.x;
    if (i < N) {
        float acc = 0.0f;
        int base = threadIdx.x;
        #pragma unroll 8
        for (int j = 0; j < K; ++j)
            acc += tileA[base + j] * tileB[j];
        C[i] = acc;
    }
}

extern "C" void solve(const float* A, const float* B, float* C, size_t N, size_t K) {
    constexpr int BLOCK = 256;
    int r = (int)(K - 1) / 2;
    int grid = ((int)N + BLOCK - 1) / BLOCK;
    size_t shmem = (BLOCK + 2 * r + (int)K) * sizeof(float);
    cudaFuncSetAttribute(conv1d_tiled<BLOCK>,
        cudaFuncAttributeMaxDynamicSharedMemorySize, 100 * 1024);
    conv1d_tiled<BLOCK><<<grid, BLOCK, shmem>>>(A, B, C, (int)N, (int)K, r);
}
Shared-memory budget for K=8191, BLOCK=256: (256 + 8190 + 8191) * 4 B ≈ 65 KB. Over the default 48 KB limit — opt in via cudaFuncSetAttribute. On T4 the cap is 64 KB; you'd have to shrink BLOCK or read B through the read-only cache.

Top row: input A. Bottom: output C[i]. Highlighted window: K inputs that contribute to C[i], multiplied by B[0..K-1] and summed. Dashed cells: out-of-bounds positions contributing 0.

21.4 Tuning levers, in order

  1. BLOCK 128 / 256 / 512. Bigger amortizes halo (2r / BLOCK shrinks). Smaller fits more blocks per SM.
  2. Outputs per thread. 2, 4, or 8 outputs per thread: same shared tile, multiple FMAs per K step, lower thread overhead.
  3. Vectorize tile loads via float4*.
  4. Unroll factor #pragma unroll 4 or 8.
  5. Interior / edge split: branch-free inner loop for blocks not touching the boundary, separate kernel for the boundary blocks.

  • Diff against a CPU reference for N=64, K=5.
  • Test K=1 (identity), large K hitting both boundaries.

22. Performance & profiling

22.1 The roofline model in one paragraph

Plot achieved throughput vs arithmetic intensity (FLOPs done per byte moved from DRAM). Memory-bandwidth-bound region = sloped line: more compute per byte → more FLOP/s. Compute-bound region = a flat ceiling at the GPU's peak. The "ridge point" is the AI where the two meet (for H100 FP32 ~20 FLOPs/byte; for FP16 tensor cores ~300).

For conv-1d: naive AI = 2K / (4K) = 0.5 (deeply memory-bound). Tiled AI ≈ 2K / 4 = K/2 = ~4000 (potentially compute-bound). That's a 4000× improvement in arithmetic intensity from one optimization — this is why tiling matters.

22.2 Occupancy

Fraction of theoretical max warps an SM can run concurrently. Three things limit it: register count, shared memory per block, threads per block. cudaOccupancyMaxActiveBlocksPerMultiprocessor tells you which. Higher is not always better — 50% occupancy is often enough to hide latency, and crippling per-thread registers to gain occupancy can backfire.

22.4 nsight compute metrics that matter

  • Memory Throughput — achieved HBM bandwidth as % of peak. Push up if memory-bound.
  • SM Throughput — how busy SMs are with math. Push up if compute-bound.
  • L1 / L2 Hit Rate — if low while memory-bound, add tiling.
  • Achieved Occupancy — if very low (<25%) and memory-bound, look for stalls.
  • Warp Stall Reasons — "Long Scoreboard" = waiting on global; "Short Scoreboard" = waiting on shared; "Wait" = barrier.
