1 Attention Basics — 60-second recap

Transformer attention computes, for every query token, a weighted sum over all key/value tokens. The weight for pair (i, j) is softmax(q_i · k_j / √d). Cost = O(N²) in sequence length.

Dense attention matrix — every Q token attends to every KV token

2 Standard Padded Batching

GPUs need rectangular tensors. When 3 sequences have lengths 5, 8, and 3 tokens, you pad shorter ones to max_len=8, producing a [B=3, S_max=8, D] tensor. The gray cells are real memory allocations that compute nothing useful.

Why this is severe for video training A mixed-resolution batch might pair a 1024×1024 video (huge token count) with a 256×256 clip. Every other sample gets padded to the largest sequence — wasting massive GPU memory and FLOPS.

3 Block-Sparse Attention (VSA)

VSA groups tokens into 64-token blocks and uses a learned top-k pattern to decide which Q-blocks should attend to which KV-blocks. A Q-block only touches its k selected KV-blocks — all others are skipped entirely.

Block-sparse attention map — rows = Q-blocks, cols = KV-blocks — animated highlight shows the active thread block

Skipped block (never touched)
Active thread block (animated)
variable_block_sizes — the last block is often partial The last KV-block in a sequence may contain fewer than 64 real tokens. The tensor variable_block_sizes[kv_block_idx] records how many real tokens each block has. Inside the kernel, columns beyond that count are masked to −∞ before softmax.

4 Inside the Triton Kernel — how pid maps to work

The Triton kernel runs thousands of thread blocks in parallel, each identified by a program ID (pid). The current kernel uses a 2D launch grid where the two axes encode which Q-block and which (batch, head) pair each thread block handles.

Current grid layout — grid = (Tq÷64, B×H, 1)

The actual code from the Triton kernel that performs this mapping:

fastvideo-kernel/python/fastvideo_kernel/triton_kernels/block_sparse_attn_triton.py : 74–83
# ----- program-id mapping -----
q_blk   = tl.program_id(0)   # Q-tile index (0 … Tq//64 - 1)
off_hz  = tl.program_id(1)   # fused (batch, head) index
b       = off_hz // H          # recover batch index
h       = off_hz %  H          # recover head index
q_tiles = N_CTX_Q // BLOCK_M   # Q-blocks per sequence — SAME for every batch item!

# Flat index into sparse connectivity tensor [B, H, q_tiles, max_kv_blks]
meta_base = ((b * H + h) * q_tiles + q_blk)

kv_blocks = tl.load(q2k_num + meta_base)       # how many KV blocks to attend to
kv_ptr    = q2k_index + meta_base * max_kv_blks  # pointer to KV block index list
The hidden assumption q_tiles = N_CTX_Q // BLOCK_M is computed once and assumed equal for every batch item. This only holds when all sequences in the batch share the same length — i.e., padded batching. It completely breaks for variable-length packing.

5 What "VarLen" Actually Means

"Variable-length" does not mean Q and KV have different lengths within one sequence. It means: concatenate multiple sequences of different lengths into a single flat tensor and process them all in one kernel launch, using cumulative length arrays (cu_seqlens) as bookmarks. This is exactly the contract that flash_attn_varlen_func implements.

Sequence packing — 3 sequences become one flat tensor, zero padding

cu_seqlens[i] to cu_seqlens[i+1] is sequence i's slice in the flat tensor. This replaces padding entirely.

6 Why the Python Loop is Wrong

The current video_sparse_attn_varlen in ops.py handles the flat tensor by simply slicing it per-sequence in a Python for-loop and calling video_sparse_attn on each slice:

fastvideo-kernel/python/fastvideo_kernel/ops.py : 97–125
for i in range(batch):
    q_s = cu_seqlens_q[i].item()      # ← CPU/GPU sync on every iteration
    q_e = cu_seqlens_q[i+1].item()

    q_i = q[q_s:q_e].unsqueeze(0).transpose(1,2).contiguous()
    k_i = k[kv_s:kv_e].unsqueeze(0).transpose(1,2).contiguous()
    v_i = v[kv_s:kv_e].unsqueeze(0).transpose(1,2).contiguous()

    out_i = video_sparse_attn(q_i, k_i, v_i, ...)  # ← 1 kernel launch per sequence
    outputs.append(out_i.squeeze(0).transpose(0,1))

return torch.cat(outputs, dim=0)

Two fundamental problems Yunsheng identified:

1

Launch overhead. Every iteration triggers a separate GPU kernel launch. The CPU must schedule each one independently. With 64 sequences per batch, that's 64 kernel launches — and each gap is dead time where the GPU is sitting idle waiting for the CPU scheduler.

2

SM underutilization. While Kernel 0 runs, the GPU's SMs can only work on Seq 0's thread blocks. Seq 1 and Seq 2 haven't been launched yet, so their work can never overlap. Parallelism across sequences is completely lost.

3

.item() sync stalls. Each cu_seqlens[i].item() call copies a GPU tensor value to CPU, which forces a CPU/GPU synchronization barrier — draining any remaining pipeline parallelism.

Yunsheng Ni's exact words (issue #917) "A Python for loop is an anti-pattern for this and introduces severe performance regressions. It triggers N separate kernel launches instead of 1, causing CPU scheduling overhead to dominate. It prevents the GPU from scheduling blocks across different sequences in parallel, destroying hardware occupancy. The fix must be implemented at the kernel level."

7 True Kernel-Level VarLen — One Launch

The correct solution makes the Triton kernel itself understand the packed format. All sequences' thread blocks are in the same grid and the GPU SM dispatcher can schedule them all simultaneously.

Correct approach — single kernel, all sequences in parallel

The key challenge: given a global pid(0), the kernel must figure out which sequence it belongs to and what its local Q-block index is within that sequence. This is done with a binary search on the cumulative block count array.

Binary search: global pid → (sequence id, local block index)

Once the kernel knows (seq_id, local_blk), it can also enforce sequence isolation: any KV-block index in the sparse list that falls outside this sequence's KV range gets its attention score masked to −∞, preventing cross-sequence leakage.

8 What Must Change — Concretely

Side-by-side of current kernel logic vs. what varlen requires:

Current — Batched (breaks for varlen)

# Grid: (Tq//64, B*H, 1)
q_blk  = tl.program_id(0)
off_hz = tl.program_id(1)
b      = off_hz // H
h      = off_hz %  H

# Same q_tiles for all — wrong!
q_tiles = N_CTX_Q // BLOCK_M
meta_base = (b*H + h) * q_tiles + q_blk

# Per-batch stride
q_off = b * stride_qz + h * stride_qh

Required — VarLen (flat packed)

# Grid: (total_q_blocks, H, 1)
global_q_blk = tl.program_id(0)
h            = tl.program_id(1)

# Binary search to recover seq id
b = searchsorted(cu_seqlens_q_blks,
                  global_q_blk)
local_q_blk = global_q_blk -
    tl.load(cu_seqlens_q_blks + b)

# Flat token offset
q_off = tl.load(cu_seqlens_q+b)*stride_qt
        + h * stride_qh

The full list of changes:

  • Kernel signature — block_sparse_attn_triton.py: Add cu_seqlens_q, cu_seqlens_kv, and cu_seqlens_q_blocks pointer parameters to _attn_fwd_sparse
  • pid mapping: Replace the q_blk / off_hz / b / h decomposition with global-pid binary search on cumulative block counts to recover (seq_id, local_q_blk, h)
  • Base pointer arithmetic: Switch from per-batch stride (b * stride_qz) to flat token offset (cu_seqlens_q[b] * stride_q_token)
  • Sequence boundary enforcement: Inside the sparse KV-block loop, mask any block whose global index falls outside [cu_seqlens_kv_blocks[b], cu_seqlens_kv_blocks[b+1]) to −∞
  • Metadata flattening — block_sparse_attn.py: q2k_idx and q2k_num must go from [B, H, q_tiles, max_kv_blks] to flat [total_q_blocks, max_kv_blks]
  • Grid update: Launch grid changes from (Tq//64, B*H, 1) to (total_q_blocks, H, 1)
  • Backward kernels: _attn_bwd_dkdv_kernel and _attn_bwd_dq_kernel need identical changes — wrong backward = wrong training gradients
  • Python wrapper — ops.py: Replace the entire Python for-loop with a single call to the new kernel passing flat tensors and cu_seqlens arrays directly
