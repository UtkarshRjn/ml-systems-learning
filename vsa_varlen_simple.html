VarLen vs Padding
— a Toy Example Guide

Everything explained with concrete small examples, no jargon. After this you'll know exactly what "sequence packing" is, how attention works across Q and KV, and why a Python loop isn't enough.

1

What are Q, K, V — and what does "attending" mean?

Before anything else, let's nail down Q, K, V with the simplest possible picture.

The idea in plain English

Imagine you have a sentence: "cat sat on mat" (4 tokens).

In self-attention, each token asks: "which other tokens are most relevant to me?"

  • Q (query) — the token doing the asking. "I am token X, what should I look at?"
  • K (key) — all tokens being looked at. "Here is what I am about."
  • V (value) — the actual content to pull from. "If you pick me, here is what you get."

The attention score between Q token i and K token j is: score(i,j) = dot(Q_i, K_j). High score → token i pays more attention to token j's value.

Each row sums to 1 after softmax. "cat" mostly attends to itself (0.7) but also glances at "mat" (0.15). This is the full 4×4 attention matrix for one sequence.

Important: Q and KV can have different lengths!

In self-attention (used in video generation): Q, K, V all come from the same sequence. Q length = KV length = sequence length.

But in cross-attention (e.g. text-to-video): Q comes from the video tokens, K and V come from the text tokens. Q length ≠ KV length.

However — the "N_CTX_Q ≠ N_CTX_KV" that the VSA kernel already supports is just this basic asymmetry. That's not what "varlen" means. Keep reading.

Why padding is painful at video scale

In NLP sentences differ by maybe 10–20 tokens — padding waste is small.

In video training, a 1024×1024 frame at 30fps might be 60,000 tokens. A 256×256 frame might be 4,000 tokens. If they're in the same batch, every 256×256 sample gets padded to 60,000 tokens — 93% of that sample's GPU memory and compute is pure waste.

Key takeaway from this section

Padding is necessary for the GPU but it wastes memory. You must mask PAD tokens to −∞ so they don't pollute attention scores. The two operations (padding + masking) together give you correct results — but at the cost of wasted compute.

Sequence Packing (VarLen) — the zero-waste alternative

Instead of padding shorter sequences, what if we just glue them together into one long flat sequence and remember where each one starts and ends?

Sent. A · tokens 0–2
Sent. B · tokens 3–7
cu_seqlens = [0, 3, 8]
This tiny array is all the bookkeeping needed: sequence 0 = tokens [0, 3), sequence 1 = tokens [3, 8)

What cu_seqlens is

cu_seqlens stands for "cumulative sequence lengths". It's just a small integer array where:

  • cu_seqlens[0] = 0 (always starts at 0)
  • cu_seqlens[1] = 3 (Sentence A ends at position 3)
  • cu_seqlens[2] = 8 (Sentence B ends at position 8 = total tokens)

To get sequence i: slice flat_tensor[ cu_seqlens[i] : cu_seqlens[i+1] ]

For a batch of 10 sequences, cu_seqlens has just 11 numbers. That's the entire overhead.

Now the critical question: when we run attention on this flat tensor, how do we prevent "cat" from attending to "dogs"? They're in the same flat tensor now — the kernel must be told where the boundaries are.

What varlen gives you

  • Zero padding: 8 real tokens, 0 wasted slots (vs 10 slots with padding, 20% waste)
  • Correct attention: Each sequence only attends to itself — enforced via cu_seqlens
  • One kernel launch: All 8 tokens processed simultaneously in a single GPU call

Why the Python Loop Fails — toy example

The current code in ops.py does handle the flat tensor — but by slicing it back into separate sequences and calling the kernel on each one. Here's why that defeats the purpose.

What the Python loop does (current code, ops.py:97–125)
1

Reads cu_seqlens[0]=0, cu_seqlens[1]=3 → slices out tokens 0–2 (Sentence A)

2

Reshapes to [1, H, 3, D] and calls video_sparse_attn() → GPU kernel launch #1

3

Reads cu_seqlens[1]=3, cu_seqlens[2]=8 → slices out tokens 3–7 (Sentence B)

4

Reshapes to [1, H, 5, D] and calls video_sparse_attn() → GPU kernel launch #2

5

Concatenates outputs back together → returns [8, H, D]

The result is correct — but this is essentially the same as just running two separate attention calls. You haven't gained anything from packing.

✗ Python loop — what the GPU sees

Kernel 1
gap
Kernel 2

Sequential. While Kernel 1 runs, Seq B sits idle. Then a scheduling gap. Then Kernel 2 runs alone.

Total time = T₁ + gap + T₂

✓ True varlen kernel — what the GPU sees

Seq A blocks
Seq B blocks

One launch. Both sequences' thread blocks are in the same grid — the GPU schedules them all simultaneously.

Total time ≈ max(T₁, T₂)

The three problems with the Python loop

  • N kernel launches instead of 1. Each launch has CPU scheduling overhead (~10–100µs). With 64 sequences per batch, that's 64× the overhead. At training scale this dominates.
  • No inter-sequence parallelism. While Sequence A's kernel runs, Sequence B's data is just waiting in CPU code. The GPU can't work on both at the same time.
  • .item() stalls. Reading cu_seqlens[i].item() forces CPU↔GPU synchronization on every loop iteration — draining any remaining GPU pipeline.

What the Kernel Must Do — toy walkthrough

For true kernel-level varlen, the Triton kernel itself needs to understand the packed format. Here's exactly how, using our 8-token example.

Setup for our toy example

Flat tensor: [cat, sat, here, dogs, love, to, run, fast] — 8 tokens total

Using block size = 4 (in reality it's 64, but 4 makes it easy to visualize):

  • Sentence A (tokens 0–2) → 1 Q-block: Q-block 0 (tokens 0,1,2 + 1 pad → but with varlen, no actual padding)
  • Sentence B (tokens 3–7) → 2 Q-blocks: Q-block 1 (tokens 3,4,5,6), Q-block 2 (token 7)

cu_seqlens_q_blocks = [0, 1, 3] — Sentence A has 1 block, Sentence B has 2 blocks, total 3 blocks

How each thread block finds its sequence — binary search on cu_seqlens_q_blocks
Q-block 0
pid(0) = 0
cat, sat, here
Q-block 1
pid(0) = 1
dogs, love, to, run
Q-block 2
pid(0) = 2
fast

Walkthrough: What does Q-block 1 (pid=1) do?

1

I am thread block with pid(0) = 1. I need to know: which sequence do I belong to?

2

I do a binary search on cu_seqlens_q_blocks = [0, 1, 3]: where does 1 fit? → Between index 0 and 1 → I belong to Sequence 1 (Sentence B)

3

My local block index within Sequence B: 1 − cu_seqlens_q_blocks[1] = 1 − 1 = 0 → I am the first block of Sentence B

4

My token offset in the flat tensor: cu_seqlens_q[1] = 3 → my tokens start at flat index 3 (dogs)

5

When I loop through my sparse KV-block list, I check: does the KV block's token range fall inside [cu_seqlens_kv[1], cu_seqlens_kv[2]) = [3, 8)? If any KV block points to tokens 0–2 (Sentence A), I mask it to −∞ — blocking cross-sequence attention.

The exact difference from the Python loop

The Python loop does this reasoning in Python, one sequence at a time, before the GPU runs. The kernel does this reasoning inside the GPU, in parallel, for all thread blocks simultaneously. Same math, fundamentally different performance.

6

The Full Picture — quick summary table

Question Answer
What is a Q token vs KV token? In self-attention they're the same sequence. Q asks "what should I look at?", K answers "here's what I am", V provides the actual content. Q-length = KV-length for self-attention.
What does "varlen" actually mean? Pack multiple sequences of different lengths into one flat tensor. Use cu_seqlens to track where each sequence starts/ends. Zero padding, one tensor, one kernel launch.
How does the kernel prevent cross-sequence attention? Each thread block does a binary search on cu_seqlens to find its sequence. It then checks every KV block it tries to attend to — if the KV block is outside its own sequence's range, it masks the score to −∞.
Why is the Python loop wrong? It triggers N separate GPU kernel launches (one per sequence) instead of 1. Each launch has CPU scheduling overhead. Sequences can't run in parallel. It destroys the entire GPU efficiency benefit of packing.
What must change in the kernel? Accept cu_seqlens as input. Rewrite the pid→(batch, Q-block) mapping using binary search. Add boundary check in the KV loop. Change grid from (Tq//64, B×H) to (total_Q_blocks, H). Update backward pass too.
Why does this matter for video training? Video sequences vary wildly in length (256×256 vs 1024×1024). Padding wastes up to 90%+ of GPU memory/compute. Sequence packing eliminates this waste entirely, directly improving training speed (MFU).
