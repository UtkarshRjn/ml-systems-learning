Chipmunk, Explained Simply

A scaffolded walkthrough of Sandy Research's Chipmunk Part I — built so you can read it cold.
~12 min read no diffusion background needed 2 interactive demos 5-question quiz
The 30-second pitch. Diffusion image/video models run the same neural network 50 times to make one output. Chipmunk's bet: between step n−1 and step n, most activations barely change — so cache last step's outputs and only recompute the small fraction that meaningfully shifted. Result: 2–3.7× faster on video generation, no retraining, ~no quality loss. Everything else is plumbing to make this idea fast on a GPU.

1 · Two facts about diffusion transformers

Chipmunk hangs entirely on these two observations. If you remember nothing else, remember these.

Fact A — Activations change slowly across denoising steps

A diffusion model takes a noisy latent and gradually denoises it over (say) 50 steps. The intermediate activations — the values flowing through attention and MLP layers — drift gradually from step to step. Step 27's activations look a lot like step 26's.

Think of a video where each frame is 95% the same as the last. You'd be wasteful to recompute every pixel from scratch every frame.

Fact B — Inside any one step, attention and MLP outputs are sparse

  • Attention sparsity. A query token doesn't attend equally to all keys. Most of its softmax probability mass concentrates on a small set of keys. So the output is essentially a weighted sum of just a few value vectors — the rest contribute near-zero.
  • MLP sparsity. After the GeLU/ReLU nonlinearity, most intermediate activations are tiny. So the final output is dominated by a few rows of W2 — the rest barely matter.
Quantitatively, the paper finds 5–25% of the values explain 70–90% of the activation change between steps. That's the gap Chipmunk exploits.

2 · The delta insight

Both attention and MLP have the same shape:

output = Σᵢ (some scalar weight) × (some value vector)
  • Attention: scalar = softmax probability, value = a row of V
  • MLP: scalar = GeLU(intermediate), value = a row of W2

An output is just a weighted sum of value vectors. Now the trick. If between steps only a few of those scalar weights changed meaningfully, then:

output_n  =  output_{n−1}
              −  (old contributions that no longer apply)
              +  (new contributions that just kicked in)

That's a delta update. You're not recomputing the whole sum — you're patching only the parts that changed.

A spreadsheet with 1,000 formulas. Change one cell — you don't recompute every formula, just the ones that depend on that cell. Chipmunk does this for neural network activations across diffusion steps.

3 · Why GPUs hate naive sparsity

The naive plan: at each step, find the few output positions whose contribution changed, and recompute only those. The problem: GPUs don't love sparsity. They love big, contiguous blocks of computation — typically 128 to 256 elements wide, fed into tensor cores.

If you ask a GPU to "load these 17 random rows from memory," it bottlenecks on memory addressing, breaks coalescing, and underutilizes tensor cores. So you have a tension:

Math wants:
Unstructured sparsity — any individual element can be picked.
Hardware wants:
Dense blocks of 128+ contiguous elements.

The whole second half of the paper reconciles these.

4 · The clever fix, part 1 — column packing

Attention's output is softmax(QK^T) @ V. If you pick a subset of keys/values you care about (say 100 out of 4,500), you can:

  1. Gather those 100 columns of K^T and 100 rows of V from anywhere in HBM (slow, scattered).
  2. Pack them contiguously into a 100-element-wide dense tile in SRAM (shared memory).
  3. Run a normal dense GEMM on the packed tile.

This works because reordering the picked columns of K^T (and rows of V) doesn't change the final output — it's a permutation followed by a sum, and sums are permutation-invariant.

Chipmunk gets the math of fine-grained sparsity but the compute pattern of dense GEMM. They call this [128, 1] column sparsity: chunks of 128 query tokens share the same set of selected keys, and the keys themselves can be picked at fine granularity.

How does the "gather" actually happen?

The previous demo glosses over the mechanism. Here's the real flow when Chipmunk pulls those scattered columns out of HBM. Click Next step to walk through it stage by stage, and toggle Compare dense to see what the GPU wishes it could do instead.

Four stages: top-k indices → address generation → scattered HBM accesses → packed SRAM tile. Each scattered load goes to a different DRAM bank/row, which is what makes the whole thing slower than a single dense load of the same number of bytes.
Picked column / load Packed in SRAM HBM bank (cold) Dense (contiguous)
The scattered HBM access pattern is the real cost. Six columns of 64 bytes each = 384 bytes total — but instead of one 384-byte coalesced load, you issue six 64-byte loads, each hitting a different DRAM bank. You pay row-activation latency multiple times, partial bank utilization, and address-generation overhead. The packing trick is how you recover dense GEMM performance after the gather.
Step by step, in CUDA-ish pseudocode: 
// Stage 1 — top-k produces a small index list
int idx[K];
top_k(scores, idx);                       // e.g. [3, 7, 12, 17, 22, 28]

// Stage 2 — turn indices into HBM addresses
for k in 0..K:
    addr[k] = K_base + idx[k] * row_stride;

// Stage 3 — issue K async loads (cp.async on Hopper)
//          each goes to a different DRAM bank → no coalescing
for k in 0..K:
    cp.async(smem_tile[k], addr[k], 64B); // 64 bytes per column slice

// Stage 4 — once loads arrive, smem_tile is dense
//          tensor cores see a normal contiguous tile
wgmma(out_tile, smem_tile, V_packed);     // dense GEMM

Zoom in: the HBM transaction timeline

"Are all K columns picked up in a single pass to HBM?" Not exactly. The K loads issue in parallel, but each one is individually less efficient than a coalesced load would be. The diagram below makes the difference visceral — same useful bytes loaded in both cases, very different wall-clock and bandwidth utilization.

Side-by-side: sparse loads vs dense load
Row activation (~10s of ns) Useful 64B (sparse) Useful 64B (dense) Wasted burst bytes
The K loads run in parallel, not in K sequential passes — the GPU's memory subsystem can have hundreds of transactions in flight. The penalty for sparsity isn't "K times slower"; it's ~50–60% of peak HBM bandwidth instead of ~90%+, because each scattered load (a) activates its own DRAM row, (b) underutilizes its DRAM burst, and (c) breaks warp coalescing. Net throughput per byte is lower, but you only pay for the K bytes you actually want.
This is also why Chipmunk uses cp.async instead of TMA on Hopper. TMA is faster (zero address-generation overhead) but it requires a contiguous multi-dim region — incompatible with column-level scatter. Sandy Research's Part III blog explicitly notes the cp.async path retains "85–90% of the dense-kernel performance" — the price they pay for fine-grained sparsity.

5 · The clever fix, part 2 — voxel reordering

Tokens in a video are usually laid out in raster order (row-major, frame by frame). Bad: token 1 and token 1000 may be spatially adjacent in the actual video but far apart in the sequence.

If 128 contiguous tokens have to share a sparsity pattern, you want those 128 tokens to be similar — because similar tokens probably attend to similar keys. So Chipmunk reorders tokens once at the start so each 128-chunk corresponds to a contiguous spatial voxel (a small 3D block of pixels across a few frames). Undo the reorder before the final decode.

Grading 1,000 student essays. You can grade alphabetically (raster), or pre-sort by topic (voxel). Sorting by topic gets you into a rhythm — same vocabulary, same expected answers, faster grading.
Try it · Raster vs voxel order
A 16×16 image. Each cell is colored by which 128-chunk it belongs to (4 chunks of 64 cells in this scaled-down demo). Toggle the layout — voxel order keeps spatially-similar tokens in the same chunk.
Voxel reordering helps attention by ~1.2×, but the paper notes near-zero impact on MLP. Why? MLPs don't mix across tokens — each token is processed independently, so reordering them is invariant to MLP. This unexplained asymmetry is one of the angles for a critique paper.

6 · What actually happens at step n

Walking through one full step now that you have all the parts:

  1. Find what changed. Compare current step's keys/queries to cached ones. Use a fast approximate top-k kernel to pick the columns whose contribution shifted most.
  2. Reorder & pack. Gather those columns from HBM, pack them into dense SRAM tiles.
  3. Run the small dense GEMM. Compute the delta — what to add and subtract.
  4. Apply to cache. output_n = output_{n−1} + delta.
  5. Write back. Update the cache for next step. (Chipmunk overlaps this writeback with the next step's compute via TMA tricks.)

Most steps are "sparse." Every ~10th step is a full dense step that re-anchors the cache, so error doesn't accumulate.

8 · Self-check

Q1. Why does the delta-update trick work for diffusion but not for a one-shot image classifier?
Right answer is the second one. The whole premise is that you have a useful cache from a previous, similar computation. One-shot inference offers nothing to delta against.
Q2. Why does Chipmunk pack scattered columns into SRAM instead of just running a sparse-aware kernel directly on HBM?
First answer. SRAM is much smaller than HBM — it's the speed difference and the dense compute pattern that matter.
Q3. Voxel reordering helps attention but is near-useless for MLP. Why?
Second answer. This asymmetry is unexplored in the paper and is a real opening for a critique. Could MLP benefit from a different reordering — say by neuron co-firing patterns?
Q4. Chipmunk does a dense step every ~10 sparse steps. What's the dense step doing?
Second answer. Sparse deltas approximate; without periodic full passes, drift accumulates.
Q5. Which of these would be the weakest setup for Chipmunk?
Second answer. Chipmunk's whole premise is that activations change slowly between steps. Few-step distilled models violate that — the paper itself flags this as a limitation.

9 · Glossary

Diffusion stepOne forward pass that nudges the noisy latent slightly closer to the final image. 50 steps = 50 forward passes.
ActivationNumerical values flowing between layers during a forward pass.
CacheA stored copy of last step's outputs so you can do delta updates.
Top-kPick the k largest values from a list. "Approximate top-k" means good enough, much faster.
Column sparsity [128, 1]Chunks of 128 rows share a sparsity pattern; columns within can be picked individually.
VoxelA small 3D block of pixels (across spatial + temporal dims). 3D analog of a 2D patch.
GEMMGeneral Matrix Multiply — the dense matmul GPUs are optimized for.
HBM / SRAMGPU memory tiers. HBM = big, slow. SRAM = small, very fast. HBM→SRAM transfers are often the bottleneck.
TMATensor Memory Accelerator — Hopper hardware that loads multidim tensors from HBM to SRAM in one instruction.
Warp-specializationSplitting GPU threads into "producer" warps (load) and "consumer" warps (compute) to overlap memory and math.
