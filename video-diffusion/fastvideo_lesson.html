Concept What is a GPU Kernel?

A kernel is a function designed to run on a GPU. Unlike regular CPU code that executes one instruction at a time, a kernel launches thousands of threads simultaneously, each handling a small piece of the computation.

Analogy: Sorting Mail

CPU approach: One person opens each letter, reads the address, and puts it in the right mailbox. One at a time. 100 letters = 100 steps.

GPU (kernel) approach: 100 people each grab one letter and put it in the right mailbox simultaneously. 100 letters = 1 step.

Concept Why Custom Kernels?

PyTorch already runs operations on the GPU. So why write custom kernels? The answer is kernel fusion — combining multiple operations into one to avoid expensive memory round-trips.

The Memory Wall Problem

GPU Memory Hierarchy: +-----------------------------------+ | Registers | ← Fastest (per thread) | ~1 cycle | +-----------------------------------+ | Shared Memory (SRAM) | ← Fast (per block) | ~5 cycles | 48-164 KB +-----------------------------------+ | L2 Cache | ← Medium | ~50 cycles | ~40 MB +-----------------------------------+ | Global Memory (HBM/DRAM) | ← Slow! | ~500 cycles | 40-80 GB +-----------------------------------+ Reading from HBM is ~100x slower than SRAM! Every separate PyTorch op = read from HBM + write back to HBM

Unfused vs Fused Operations

PyTorch default (4 separate kernels): Step 1: scores = Q @ K.T -> write 500MB to HBM Step 2: scores = scores / sqrt(d) -> read 500MB, write 500MB Step 3: probs = softmax(scores) -> read 500MB, write 500MB Step 4: out = probs @ V -> read 500MB, write result Total HBM traffic: ~3 GB (read + write each step) Kernel launches: 4 GPU idle time between launches: significant
Custom fused kernel (1 kernel): +------------------------------------------+ | Load Q block into SRAM | | Load K block into SRAM | | scores = Q_sram @ K_sram.T (in SRAM) | | scores /= sqrt(d) (in SRAM) | | probs = softmax(scores) (in SRAM) | | Load V block into SRAM | | out = probs @ V_sram (in SRAM) | | Write final output to HBM | +------------------------------------------+ Total HBM traffic: ~50 MB (just Q, K, V in + output) Kernel launches: 1 Speedup: 5-10x for memory-bound ops!

Triton: Making Kernels Accessible

Triton (by OpenAI) lets you write GPU kernels in Python-like syntax instead of CUDA C++. FastVideo uses Triton for its sparse attention kernels.

Triton kernel example (simplified): @triton.jit def add_kernel(x_ptr, y_ptr, out_ptr, N, BLOCK: tl.constexpr): # Each thread block handles BLOCK elements pid = tl.program_id(0) # Which block am I? offsets = pid * BLOCK + tl.arange(0, BLOCK) # My data indices mask = offsets < N # Bounds check x = tl.load(x_ptr + offsets, mask=mask) # Load from HBM y = tl.load(y_ptr + offsets, mask=mask) # Load from HBM tl.store(out_ptr + offsets, x + y, mask=mask) # Write result

Concept Attention Mechanism

Attention is the core operation in transformers. It lets each token "look at" all other tokens to understand context. The formula is:

Attention(Q, K, V) = softmax(Q × KT / √d) × V

Where Q = queries, K = keys, V = values, d = head dimension

Concept The Quadratic Cost Problem

Video diffusion models process thousands of tokens (each frame patch = 1 token). Dense attention scales as O(N²), which becomes the bottleneck:

Scaling: How attention cost grows with sequence length
Sequence LengthDense Attention OpsTime (relative)
256 tokens (1 image)65,5361x
1,024 tokens (short clip)1,048,57616x
4,096 tokens (video)16,777,216256x
16,384 tokens (long video)268,435,4564096x
The core insight: In most attention matrices, the majority of weights are near-zero after softmax. We're spending compute on entries that contribute almost nothing to the output. What if we only computed the important entries?

Practice Sparse Attention & VSA

Video Sparse Attention (VSA) solves the quadratic problem by only computing attention for the most relevant blocks. It divides the sequence into blocks and selects the top-k most important K/V blocks per Q block.

How VSA Works (Step by Step)

1. Divide into Blocks
Split Q and KV into blocks of 64 tokens each
↓
2. Score Blocks
Compute rough importance of each KV block for each Q block
↓
3. Select Top-K
Keep only the k most relevant KV blocks per Q block
↓
4. Compute Sparse Attention
Only compute attention between Q blocks and their selected KV blocks

Practice Variable Length (Varlen) Support

The current VSA kernel requires Q and KV to have the same sequence length. This is the limitation that issue #1040 addresses.

Why Different Lengths?

Real-world scenario: Text + Video input
Text:
3 tokens
Video:
100 tokens
Q seq:
80 tokens (video queries)
KV seq:
120 tokens (text + video keys)
len(Q) != len(KV) → Current VSA REJECTS this!

The Fix: Separate Block Tracking

Current kernel parameters: N_CTX = 512 ← SINGLE length for both! BLOCK_SIZE = 64 num_blocks = 512 / 64 = 8 Q blocks: [blk0][blk1][blk2][blk3][blk4][blk5][blk6][blk7] KV blocks: [blk0][blk1][blk2][blk3][blk4][blk5][blk6][blk7] | | | | | | | | FORCED to be same count variable_block_sizes: [64, 64, 64, 64, 64, 64, 64, 64] (single tensor shared for both Q and KV) If Q has 300 tokens and KV has 500: ERROR: sequence lengths must match!
Fixed kernel parameters: N_CTX_Q = 384 ← Separate Q length N_CTX_KV = 512 ← Separate KV length BLOCK_SIZE = 64 Q: 6 blocks [blk0][blk1][blk2][blk3][blk4][blk5] KV: 8 blocks [blk0][blk1][blk2][blk3][blk4][blk5][blk6][blk7] q_variable_block_sizes: [64, 64, 64, 64, 64, 24] ← 6 entries kv_variable_block_sizes: [64, 64, 64, 64, 64, 64, 64, 56] ← 8 entries Last blocks may be partially filled ^ Q=300 tokens, KV=500 tokens: Padded to 384 and 512 respectively Each tracked independently

Varlen Batching (like Flash Attention)

flash_attn_varlen_func style batching: Batch of 3 sequences with DIFFERENT lengths: Seq A: Q=100, KV=150 Seq B: Q=200, KV=200 Seq C: Q=50, KV=300 Packed flat (no padding between sequences): Q: [---Seq A (100)---][------Seq B (200)------][Seq C (50)] KV: [----Seq A (150)----][------Seq B (200)------][------Seq C (300)------] cu_seqlens_q = [0, 100, 300, 350] ← cumulative Q lengths cu_seqlens_kv = [0, 150, 350, 650] ← cumulative KV lengths Each sequence processed independently: +-------------------------------------------------------+ | Seq A: sparse_attn(Q[0:100], KV[0:150]) different | | Seq B: sparse_attn(Q[0:200], KV[0:200]) same OK | | Seq C: sparse_attn(Q[0:50], KV[0:300]) different | +-------------------------------------------------------+ Goal: VSA should support this pattern!
